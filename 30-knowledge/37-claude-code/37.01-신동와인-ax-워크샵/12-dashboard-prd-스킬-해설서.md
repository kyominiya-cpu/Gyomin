핵심 설계 원칙: "결정 우선(Decision-First)"
이 스킬의 모든 질문과 제안은 하나의 원칙에서 출발합니다:
"이 대시보드를 보고 어떤 결정을 내리는가?"
이 질문에 답이 없는 차트는 만들지 않습니다. 예쁜 그래프, 인상적인 숫자, "있으면 좋을 것 같은" 데이터 -- 모두 이 질문을 통과해야 대시보드에 들어갑니다.
이유: 대시보드는 보고서가 아닙니다. 의사결정을 돕는 도구입니다. 매일 아침 열어서 "오늘 뭘 해야 하지?"에 답을 얻는 화면이어야 합니다.
동작 방식: 4단계 대화
스킬을 실행하면 4단계에 걸쳐 대화가 진행됩니다. 각 단계에서 질문은 한 번에 하나씩, 구체적인 예시와 함께 제시됩니다.
Phase 1: 의사결정과 고민 (사용자가 아는 것)
목적: 대시보드의 존재 이유를 명확히 합니다.
4개 질문을 순서대로 진행합니다:
Q1. "이 대시보드를 보고 어떤 결정을 내리고 싶은가?"
이것이 첫 번째 질문인 이유가 있습니다. 기능이나 데이터가 아니라 결정에서 시작합니다. "매출 그래프를 보고 싶다"가 아니라 "부진한 매장에 프로모션을 걸지 결정하고 싶다"가 올바른 답입니다.
예시:
"이번 달 매출이 목표 대비 어떤지 보고, 부진한 매장에 프로모션을 걸지 결정"
"어떤 상품이 잘 팔리는지 보고 다음 달 발주량을 조정"
"직원별 실적을 보고 인센티브 지급 여부를 판단"
Q2. "지금 그 결정을 내리려면 어떤 과정을 거치나? 어디서 막히나?"
현재의 Pain Point를 파악합니다. 이 답변이 PRD의 "배경" 섹션이 됩니다.
예시:
"엑셀 3개 파일을 열어서 수작업으로 합치는데 2시간 걸림"
"매장별로 카톡으로 보고받는데, 숫자가 안 맞을 때가 많음"
"월말에 한 번 보는데, 그때는 이미 늦음"
Q3. "누가, 얼마나 자주 보나?"
이 답변으로 대시보드 유형을 결정합니다:
답변 패턴
	
대시보드 유형
	
특성


"나(대표)만 매일 아침"
	
운영 대시보드
	
실시간~일간 갱신, 이상 탐지 중심


"경영진이 주 1회 회의에서"
	
전략 대시보드
	
월간~분기, 트렌드/목표 대비


"팀장들이 매일, 경영진이 주 1회"
	
전술 대시보드
	
일간~주간, 액션 연결


"분석가가 필요할 때 깊이 파고들기 위해"
	
분석 대시보드
	
필터/세그먼트 풍부
유형에 따라 KPI 수, 갱신 주기, 차트 복잡도가 달라집니다.
Q4. "대시보드에서 가장 먼저 눈에 들어왔으면 하는 숫자는?"
핵심 KPI 후보를 뽑습니다. 대시보드 메인 화면 좌상단에 놓을 숫자입니다.
Phase 1 마무리: 답변을 종합하여 요약합니다.
핵심 의사결정 목록
Pain Points 요약
대시보드 유형 판정
KPI 후보 목록
"이 정리가 맞나요?" 확인
Phase 2: 데이터 현실 파악 (사용자가 부분적으로 아는 것)
목적: 실제 데이터를 확인하고, Phase 1의 욕구가 실현 가능한지 검증합니다.
Q5. "데이터가 어디에 있나? 파일 경로가 있으면 공유해주세요."
여기서 이 스킬의 핵심 기능이 작동합니다. 사용자가 파일 경로를 알려주면, Claude가 파일을 직접 열어서 구조를 자동 분석합니다.
예를 들어 일룸 시연 데이터를 넣으면:
> Loading Plain Text code…
​
Claude가 Read 도구로 각 파일을 열고 자동 분석 리포트를 생성합니다:
> Loading Plain Text code…
​
사용자가 파일을 하나하나 열어볼 필요가 없습니다. Claude가 대신 읽고 "이 파일은 이런 구조입니다"라고 알려줍니다.
파일이 아직 없으면 구두 설명으로도 진행 가능합니다. PRD에 [파일 확인 후 상세화 필요] 마커를 남겨서 나중에 보완할 수 있게 합니다.
Q6. "데이터들을 연결하는 공통 키가 있나?"
"모르겠습니다"라고 답해도 됩니다. Claude가 파일에서 직접 찾아봅니다.
일룸 사례에서는:
ERP의 "대리점코드"와 목표실적의 "매장코드"가 같은 것
상품코드가 채널마다 다름 (LP-1200 / NV-LP1200 / OH-LP1200)
상품기준시트가 이 매핑을 담당
이런 것들을 Claude가 파일 분석에서 발견하고 알려줍니다.

Phase 1에서 파악한 욕구와 Phase 2에서 확인한 데이터 현실을 비교합니다:

목표실적.csv + ERP 수주 있음
	
가능


상품별 판매 순위
	
상품별 매출 집계
	
코드 매핑 필요 (상품기준시트 활용)
	
가능 (추가 작업 필요)


실시간 재고 현황

현재 데이터에 없음

"불가"인 항목은 대시보드에서 빠지거나, 추가 데이터 확보 후 반영합니다. 이 Gap Analysis가 비현실적인 PRD가 만들어지는 것을 방지합니다.
Phase 3: 대시보드 화면 설계 (공동 창작)
목적: 실제 화면 구성을 사용자와 함께 설계합니다.
이 단계에서 Claude는 내부적으로 설계 원칙 문서를 참조합니다. 이 원칙들은 데이터 시각화 분야의 검증된 방법론을 정리한 것입니다.
Q8. View 제안
Phase 1+2 결과를 바탕으로 2~4개 View(화면)를 제안합니다.
예시 제안:
> Loading Plain Text code…
​
각 차트에 선택 이유가 포함됩니다. "왜 꺾은선인가?", "왜 파이차트가 아닌가?" 등을 설명합니다.
제안 후 사용자에게 묻습니다: "수정/추가/삭제할 부분이 있으신가요?"
사용자는 설계를 처음부터 할 필요 없이, 제안을 보고 수정만 하면 됩니다.

Sheets를 데이터 소스로 활용
	
기존 워크플로우 유지
왜 이런 기준인가?
Google Sheets API는 SQL의 WHERE/JOIN/GROUP BY를 지원하지 않습니다. 전체 데이터를 받아서 프로그램이 직접 필터링합니다. 그래서 행 수가 많아지면 느려집니다.
API에는 분당 요청 횟수 제한(분당 60회/사용자)이 있습니다. 대시보드를 보는 사람이 많으면 이 한도에 금방 도달합니다.
10,000행 이하 + 소수 열람자라면 이 제약이 문제되지 않아 Sheets가 가장 간편한 선택입니다.
일룸 시연 사례에서는 오프라인 50~60건/월 + 온라인 160건/월 = 약 200건/월이므로, "Next.js + Recharts + Google Sheets" 조합이 추천됩니다.
공통 UI 스택 해설
기술 스택 추천에서 데이터 저장소(Google Sheets / Supabase / Metabase)는 상황에 따라 달라지지만, 프론트엔드 UI 스택은 공통입니다:
기술
	
한 줄 설명


Next.js
	
React 기반 웹 프레임워크. 페이지 라우팅, 서버 렌더링, API 엔드포인트를 하나로 묶어준다. 대시보드의 뼈대.


React
	
UI를 컴포넌트(KPI 카드, 차트, 필터 등) 단위로 조립하는 라이브러리. Next.js 안에 포함.


shadcn/ui
	
카드, 테이블, 셀렉트, 뱃지 등 자주 쓰는 UI 컴포넌트 모음. 설치하면 디자인 품질의 최소 기준선이 올라간다. 없으면 모든 컴포넌트를 처음부터 직접 만들어야 한다.


Radix UI
	
shadcn/ui의 내부 엔진. 드롭다운, 다이얼로그 같은 인터랙션의 접근성과 동작을 담당. 직접 다룰 일은 없다.


Tailwind CSS
	
CSS를 클래스 이름으로 작성하는 도구. bg-red-500, rounded-lg 같은 클래스를 조합해서 디자인한다.


Recharts
	
React용 차트 라이브러리. 꺾은선, 막대, 파이 등 대시보드에 필요한 차트를 그린다.


TypeScript
	
JavaScript에 타입을 추가한 언어. "이 변수에는 숫자만 들어와야 한다" 같은 규칙을 코드에 명시하여 오류를 줄인다.


Lucide
	
아이콘 라이브러리. 화살표, 차트 아이콘, 필터 아이콘 등.
이 스택을 선택한 이유: Claude Code가 가장 잘 다루는 조합이며, 생태계가 크고, 무료이며, 커스터마이징이 자유롭습니다.
