# 다계좌 거래내역 통합 분석 워크플로우

> 여러 은행의 거래내역 엑셀을 하나로 합쳐 자금 흐름을 추적하고,
> 결과를 HWPX 문서로 산출하는 방법. 2026-08-30 정리.

---

## 1. 문제 — 은행마다 엑셀 포맷이 다르다

같은 "거래내역 조회" 결과인데 은행별로 구조가 전부 다르다. 실제로 마주친 것만 8종.

| 은행/형식 | 헤더 행 | 컬럼 구조 |
|---|---|---|
| 국민 (KB종합통장) | 5행 | 거래일시 / 적요 / 보낸분·받는분 / 송금메모 / 출금액 / 입금액 |
| 국민 (직장인우대) | 6행 | 거래일 / 상태 / 거래구분 / 출금금액 / 입금금액 / … / 의뢰인 |
| 우리 (구형 .xls) | 4행 | No. / 거래일시 / 적요 / 기재내용 / 찾으신금액 / 맡기신금액 |
| 우리 (신형 .xlsx) | 11행 | 거래일자 / 종류 / 적요 / 지급금액 / 입금금액 (빈 컬럼 다수) |
| 신한 | 3행 | 거래일자 / 거래시간 / 적요 / 출금(원) / 입금(원) / 내용 |
| 신한 (거래구분형) | 3행 | 거래일 / 구분(입금·지급) / **거래금액 단일 컬럼** |
| 농협 | 12행 | 순번 / 거래일시 / 출금금액 / 입금금액 / 거래내용 / 거래기록사항 |
| 산업 | 14행 | 거래일시 / 거래구분 / 적요 / 출금(원) / 입금(원) |

추가로 걸리는 것들:

- **`.xls`는 진짜 OLE2 바이너리** — `xlrd` 필요 (`openpyxl` 불가). 반대로 xlrd 2.x는 `.xlsx`를 못 읽는다
- **날짜가 3가지 형태로 섞여 있음** — 엑셀 serial(float), `2015.01.02 13:06`, `2015/03/16  14:28:14`
- **시트가 연도별로 쪼개져 있음** — 한 파일에 10~11개 시트
- 금액이 `'1,234,567'` 문자열이거나 `1234567.0` float이거나

## 2. 해결 — 컬럼명 매칭 기반 범용 파서

포맷마다 파서를 만들지 않는다. **헤더 행을 찾아서 컬럼명으로 매칭**한다.

### 헤더 행 탐지

상위 30행을 훑으면서 아래 세 조건을 동시에 만족하는 행을 헤더로 본다.

```python
DATE_K = ('거래일', '일자', '거래일시')
OUT_K  = ('출금', '찾으신', '지급금액')
IN_K   = ('입금', '맡기신')
MEMO_K = ('적요', '기재내용', '내용', '거래내용', '거래기록사항',
          '보낸분', '송금메모', '의뢰인', '거래메모', '통장적요', '받는분')
```

매칭 전에 `정규화(공백·괄호·'원'·개행 제거)`를 거쳐야 `출금 (원)` 같은 변형이 잡힌다.

### 날짜 파싱

```python
def parse_date(v, datemode=0):
    # 1) 엑셀 serial (30000~60000 범위)
    # 2) YYYY[.-/]M[.-/]D 정규식
    # 3) 문자열로 온 serial
```

`30000 < v < 60000` 범위 체크로 금액과 날짜를 구분한다 (1982~2064년).

### 단일 금액 컬럼 예외

`거래금액` 하나에 `구분`(입금/지급)으로 방향을 표시하는 포맷은 위 로직에 안 걸린다.
헤더 탐지에 실패하면 **0건**으로 조용히 넘어가므로, **파일별 처리 건수를 반드시 출력**해서 확인할 것.

```
계좌7/신한     ok    0건    ← 이 0을 놓치면 계좌 하나가 통째로 빠진다
```

### 산출

```
(거래일, 계좌라벨, 출금액, 입금액, 적요)
```

5-튜플로 통일한 뒤 날짜순 정렬. 14개 계좌 · 19년치 · 14,724건이 한 리스트에 들어간다.

## 3. 분석 — 적요가 핵심이다

통합 후에는 **적요 키워드 검색**이 가장 강력하다. 사람이 직접 쓴 메모라 의도가 그대로 남아 있다.

### 유용했던 패턴

**① 자금의 꼬리 물기 추적**
입금 직후 같은 금액이 나가면 그 계좌는 경유 계좌다. 날짜순 정렬해두면 눈에 띈다.

```
09-14  입 29,000,000  [A]
09-14  출 10,000,000  [B]
09-14  출 10,000,000  [B]
09-14  출  9,000,000  [B]   → A에서 받아 B로 그대로 나감
```

**② 계좌 간 내부 이체 걸러내기**
서로 다른 계좌에 같은 날 같은 금액이 출/입으로 잡히면 **새로 생긴 돈이 아니다.**
이걸 안 거르면 총액이 부풀려진다. 실제로 한 번 잘못 집계했다가 정정했다.

**③ 적요가 사실을 증명한다**
`중도금중잔금후잔액` 같은 적요는 그 자체로 자금 용도를 서술한다.
외부에 설명해야 하는 상황에서 이런 한 줄이 표 열 개보다 낫다.

**④ 부과 명의 vs 납부 계좌**
재산세·건강보험료 적요에는 보통 **부과 대상자 이름**이 들어간다.
납부한 계좌와 부과 명의가 다르면 그 차이 자체가 정보다.

**⑤ 정기 소액 이체는 성격을 드러낸다**
매달 같은 날 같은 금액 → 이자 분담, 곗돈, 임대료, 부양비 중 하나.
전후 맥락과 합쳐 보면 관계가 읽힌다.

### 반대로 조심할 것

- **들어온 기록 없이 나간 기록만 있는 돈** — 현금 거래였을 가능성. 설명이 필요한 지점
- **이름 오타** — 기억하는 이름과 적요가 다를 수 있다 (한 글자 차이). 부분 문자열로 검색할 것
- 동일 인물이 여러 표기로 등장 (`홍길동` / `국민홍길동` / `홍길동님`)

## 4. HWPX 문서 생성 — 레퍼런스 승계 방식

분석 결과를 한글 문서로 낼 때, 템플릿을 새로 만들지 않는다.
**기존 hwpx의 `header.xml`을 그대로 재사용**하면 폰트·여백·용지가 자동으로 승계된다.

### 절차

1. 레퍼런스 hwpx에서 `Contents/header.xml`, `Contents/section0.xml` 추출
2. `header.xml`에 필요한 `charPr`/`paraPr`/`borderFill`만 **append** (기존 ID 건드리지 않음)
3. 각 그룹의 `itemCnt` 속성을 실제 자식 수에 맞춰 갱신
4. 레퍼런스 `section0.xml`의 **첫 문단 `secPr` 블록을 그대로 가져와** 새 본문 앞에 붙임
5. mimetype을 **ZIP_STORED로 첫 번째 엔트리**에 넣고 재패키징

### 마크업 → XML 빌더

원고를 한 줄 한 마커로 쓰면 편집이 쉽다.

```
T|문서 제목
H|Ⅰ. 대제목
h|1. 소제목
p|본문 (들여쓰기)
q|· 하위 항목 (깊은 들여쓰기)
C|가운데 정렬
B|빈 줄
TBL|8000,13000,27188
TR|셀1;;셀2;;셀3
```

- `**굵게**` 는 별도 `charPr`을 쓰는 run으로 분리
- 표 셀 안 줄바꿈은 `\n` 리터럴로 받아 문단 분리

### 검증 (빌드 후 필수)

```
1. ZIP 무결성 + mimetype 첫 엔트리·STORED 확인
2. 모든 XML well-formed 파싱
3. section0의 *IDRef 가 header 정의에 전부 존재하는지 (dangling 참조 0건)
4. itemCnt == 실제 자식 수
```

3번을 빼먹으면 한글에서 열 때 서식이 깨지거나 열리지 않는다.

## 5. 실무 함정 모음

| 증상 | 원인 | 대응 |
|---|---|---|
| 출력이 전부 깨진 한글 | stdout 인코딩이 cp949 | `PYTHONIOENCODING=utf-8` |
| `ImportError: cannot import name 'isgenerator'` | 스크립트 파일명이 `inspect.py` | 표준 모듈명과 겹치는 파일명 금지 |
| `Device or resource busy` | 한글이 파일을 잠금 | 프로세스 종료 후 덮어쓰기, 또는 새 이름 |
| 계좌 하나가 0건 | 헤더 탐지 실패 | 파일별 건수 로그 확인 |
| CSV 한글 깨짐 (엑셀) | BOM 없음 | `encoding='utf-8-sig'` |

## 6. 재사용 체크리스트

- [ ] 파일별 파싱 건수를 출력하고 **0건이 없는지** 확인
- [ ] 전체 기간이 예상 범위와 맞는지 (`최초 ~ 최종` 날짜 출력)
- [ ] 계좌 간 내부 이체를 중복 집계하지 않았는지
- [ ] 키워드 검색은 **부분 문자열**로 (이름 오타 대비)
- [ ] 문서 빌드 후 dangling IDRef 검사
- [ ] 민감정보(주민번호·계좌번호)가 산출물에 섞이지 않았는지 — **공유 전 필수**
